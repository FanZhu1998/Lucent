# Performance baseline, 2026-10-15 (0.1.0 release candidate)

The third measurement of Lucent's performance ([ADR 0021](../adr/0021-performance-baseline.md),
amendment of the W12 release), made by the release checklist's gate 5 on the 0.1.0 release
candidate, and the first in which every scenario started on a quiet machine (ADR 0021, decisions 15
to 17). Measured against [`budgets.json`](budgets.json), which still comes from the
[2026-10-10 baseline](baseline-2026-10-10.md), it exceeds six budgets of the preview scenario and
fails one edit budget that rests on two of its three values; the 2026-10-10 baseline's own code,
built again and measured alternately with the release candidate, exceeds the same six (below), so
the preview's change is not in the code. Which change of the machine's state it is, the data does
not establish: this run is recorded as a baseline, but the budgets are not derived from it, and
COR-5 stays open (below). Every figure of this run below comes from the JSON in
[`data/2026-10-15/`](data/2026-10-15/): the tables rendered by `tools\bench\Format-BenchReport.ps1`
from the run's files, the preview scenario measured again alone from
[`scenario-alone/`](data/2026-10-15/scenario-alone/) and the A/B measurement from
[`ab-preview/`](data/2026-10-15/ab-preview/), each run with its machine record; only the staged
layout's size was counted in the staged folder. The earlier baselines' figures come from their data
(`data/2026-10-09/`, `data/2026-10-10/`) and `budgets.json`, except the 2026-10-10 full run's
preview figures, whose JSON the scenario measured again replaced: they are quoted from
[that baseline](baseline-2026-10-10.md). The blueprint's figures are engineering targets, not claims,
and nothing here turns them into one.

- **Build:** `release` preset of branch `release/0.1.0` at commit 80409e4, the 0.1.0 release
  candidate, with nothing uncommitted, built in `build\rel-0.1.0-perf`, MSVC 19.44, triplet
  x64-windows-lucent, the bundled lens database 1.0.0 and camera support database 3.0.1. Start-up
  runs used the installed layout `tools\package.ps1 -SkipBuild -StageOnly` staged (391 files,
  73.0 MiB).
- **Harness:** `tools\bench\Invoke-LucentBench.ps1` of the same commit, all ten scenarios in the
  fixed order (thumbnails first, startup last; ADR 0021, decision 12), three repetitions after a
  discarded warm-up each, 54 min, 18:16 to 19:10 UTC.
- **The machine's state:** on AC power, Balanced plan, 2.59 GiB of memory available at the start
  (3.35 GiB on 2026-10-10), 317 processes. While the harness recorded the machine, the system used
  8.4 % of the CPU and the busiest other process 93 % of one processor; the wait before the first
  scenario then found three quiet samples within 6.2 s (2.1, 1.9 and 6.4 %, no other process above
  9 % of one processor). Every scenario started on a quiet machine (`quiet_by_scenario`): each later
  wait began with one other process at about one processor (94 to 105 % in its first samples) and
  ended after 12.3 s (16.5 s before batch-cancel) with three quiet samples.
- **Measured again:** the preview scenario alone, 19:12 to 19:15 UTC on a quiet machine
  (`build\rel-0.1.0-bench-preview`, its `preview.json` and `machine-preview.json` kept in
  `scenario-alone/`), measured the same level and failed the same six budgets; then the A/B
  measurement below, 19:31 to 19:42 UTC.
- **Reading the figures:** "median [min-max] (CV)" over the three recorded repetitions; with three
  values the nearest-rank p95 is the maximum. Per-image figures first take each image's median.
- **Not repeated:** the 1,000-file batch resilience gate (ADR 0021, decision 6), last passed on
  2026-10-09; the release checklist runs it again when the batch, worker or catalog code changed
  since its last pass.

**Gate 5.** The release checklist passes gate 5 when `Test-BenchBudgets.ps1` exits with 0, or when
each exceedance is explained in the release notes. The 0.1.0 release passes it by the release
notes: they explain the six preview exceedances as a change of the machine's state on the A/B
evidence below (ADR 0021, decision 20), and the Z 6's exposure step as a repetition that recorded
no value. The budgets stay those of 2026-10-10 (Budgets, below).

**The A/B measurement.** To tell a change of the code from a change of the machine, the code the
2026-10-10 baseline measured, as merged into main before the W12 release phase (f2faf0e: the W13
closure, committed after that measurement), was built with the release preset in a temporary
worktree and staged, and its preview scenario was measured on this machine alternately with the
release candidate's, four runs within 11 minutes with the release candidate's harness, each after
its own quiet wait:

```powershell
git worktree add --detach <worktree> f2faf0e
# in <worktree>:
powershell -NoProfile -File tools\build.ps1 -Preset release -BuildDir build\perf -Jobs 6
powershell -NoProfile -File tools\package.ps1 -BuildDir build\perf -SkipBuild -StageOnly
# in the repository at 80409e4, in this order: base1, head1, base2, head2
powershell -NoProfile -File tools\bench\Invoke-LucentBench.ps1 -BuildDir <worktree>\build\perf -OutputDir build\ab-base1 -Scenario preview
powershell -NoProfile -File tools\bench\Invoke-LucentBench.ps1 -BuildDir build\rel-0.1.0-perf -OutputDir build\ab-head1 -Scenario preview
# then the same two again into build\ab-base2 and build\ab-head2
```

The ILCE-7M4's 100 % view, for example, is slower in the release candidate in both pairs, by 5 and
2 ms: within the 500 ms over which the W13 code's own runs spread, so no regression, and with the
W13 code over the budget in both of its runs, the machine's state. Decision 20 judges exceeded
budgets only; of the four figures within theirs, the X-T4's first RAW frame alone has a pair beyond
the W13 code's spread (head2 75 ms slower against a spread of 67 ms, head1 52 ms; 3 to 4 %, within
its 2,430 ms in every run), and whether that is a difference of the builds, two pairs cannot tell.
Averaged over each build's two runs, the medians differ by at most 5 % per figure, in either
direction, where the six exceeded figures lie 28 to 60 % above 2026-10-10 in the four runs (26 to
59 % in this run); the exception is the X-T4's 100 % view, which varies most from run to run
(base2's runs 2.35, 2.39 and 3.27 s, every other run of both builds 2.90 to 3.28 s). The preview
service's full-size render took as long in both builds (the R5 0.88 to 0.90 s, every photo within
0.05 s), and the peak working sets agree within 0.6 %. **The rise against 2026-10-10 is therefore
not in the code changed since: the 2026-10-10 baseline's own code measures it on this machine
today.** The harness's changes since then (the scenario order, the quiet waits between scenarios,
the wait for a timed-out run's processes) do not change how a run is measured, and the fixtures are
the same 40 files. What remains is the machine's state.

**What differs, as far as the data shows.** Lucent.exe did the same work as on 2026-10-10: its CPU
time per preview run is within 4 % of 2026-10-10's for every photo (the R5 12.2 s against 12.6 s)
and the full-size render took as long (0.88 s against 0.93 s), but each run took longer from start
to end (the R5 6.3 s against 4.3 s). The time added lies after the photo is opened: from opening to
its first RAW frame 0.50 to 0.83 s against 0.20 to 0.32 s, and in the 100 % view. The developer
automation reads those times in its 50 ms poll, and this day they fall on the 15.625 ms default
tick of Windows' timers: in the six preview runs of the day (this run, the scenario alone and the
four A/B runs, 90 measurements of each figure), 70 % of the times from opening to the first frame
and 73 % of the 100 % views lie within 2 ms of a multiple of 15.625 ms, against 1 and 2 of the 15
in the 2026-10-10 preview scenario (chance alone: about 26 %).

**The same state on 2026-10-10.** The first part of the 2026-10-10 full run shows this signature
too. Its scenarios after the preview scenario that open a photo (edit, Auto in the editor and its
cancellation, ending at 21:42 UTC) took 0.62 to 0.88 s from opening to the first RAW frame (medians
per photo), 22 of the 33 times on the tick, as this run's same scenarios did (0.50 to 1.01 s, 21 of
33), and its own preview scenario measured this day's level (the R5's 100 % view 2.15 s, the Z 6's
2.06 s). The automation's responsiveness probe, a 5 ms timer whose median gap was 5 ms in every run
of both days, marks a change within that run: the 99th percentile of its gaps was 6 to 7 ms in the
scenarios up to Auto cancellation, as in every run of this day (6 to 10 ms), and 22 to 27 ms in the
batch scenarios (22:08 to 22:24 UTC) and 22 to 30 ms in the preview scenario measured again at
22:31 UTC, which the preview budgets come from; on 2026-10-09, whose times from opening to the
first RAW frame were 0.12 to 0.32 s, it was 19 to 58 ms in every scenario. Short stalls of the UI
thread thus went with the faster state, consistent with frames presented on screen in it and not in
the slower one. Of the kept preview runs of both days, the 2026-10-10 baseline's, measured again, is
the only one in the faster state. ADR 0021's decision 11 attributed the full run's slower previews
most likely to the antivirus scanning the cold starts' copies, which then ran first; this day's
runs measured the same level with the cold starts last and a quiet machine before every scenario.

**The candidates.** Which condition of the machine makes the difference is not established:
`machine.json` records neither the display nor the session, nor whether Lucent's window was
visible. The data supports three candidates, none of them shown to be the cause:

- *A Windows servicing update between the baselines.* `machine.json` records Windows PowerShell
  5.1.26100.9444 on 2026-10-09 and 2026-10-10 and 5.1.26100.9711 on 2026-10-15, a version Windows'
  servicing updates change (the system's version, 10.0.26200, stays the same). Both states occurred
  on 2026-10-10, before it.
- *Windows 11's timer policy.* Windows 11 does not guarantee a timer resolution finer than its
  default of 15.625 ms to a process whose windows are fully occluded, minimised or otherwise
  invisible to the user, which a display turned off or a locked session may make them. The times on
  the tick fit it, and the probe's missing stalls fit a window that presented no frames on screen;
  that the probe's 5 ms timer kept its interval shows that not every timer of the process was
  coarse.
- *Less available memory:* 2.59 GiB at the start of this run against 3.35 GiB at the start of
  2026-10-10's, and 2.59 to 2.85 GiB at the starts of the day's six preview runs against 3.62 GiB
  before the 2026-10-10 preview scenario. The first part of the 2026-10-10 full run, which started
  with 3.35 GiB, was in the slower state too, while the 2026-10-09 run, which started with 2.41 GiB,
  reached its first RAW frames as soon after opening as the 2026-10-10 preview scenario.

**Follow-up (COR-5).** The harness records the display state, whether the session is locked and
whether Lucent's window was visible (and, if it is cheap, the timer resolution in effect), and the
preview path is checked for waits that depend on the timer resolution: a latency of a whole number
of ticks points at a timer or a poll rather than at work. That check includes the measurement's own
waits: the automation reads these latencies in its 50 ms poll and, while the window presents no
frames, lays the view out by grabbing a frame at most every 250 ms
(`apps\lucent\src\developer_automation.cpp`). A baseline measured with the display on, the session
unlocked and Lucent's windows visible, and recorded as such, then closes COR-5 and derives the
budgets again (ADR 0021, decision 19).

**The other scenarios** held every budget of 2026-10-10 but the Z 6's exposure step (above). The
warm start is faster (0.76 s to the window against 0.85 s, 0.86 s to the first frame against
0.95 s): in the A/B's preview runs the release candidate's window was created 0.11 s before the W13
code's (median 0.82 s against 0.93 s, 30 runs each), consistent with the lens database now loading
off the UI thread (APL-06; about 140 ms of the UI thread in W13); the warm starts now also run last,
after a quiet wait. Lucent.exe holds a little more memory at start (the warm start's working set
188 MiB against 174 MiB, the five-photo library's 214 MiB against 198 MiB) and in Auto in the editor
(about 30 MiB more peak commit for every photo), and less during batches (162 MiB against 172 MiB
for the five-photo JPEG batch); the 16-bit TIFF export is 6 % slower over all images (median 7.66 s
against 7.21 s), the automatic batch of all fixtures 8 % faster (13.9 against 12.9 photos per
minute). These were not measured against the W13 code, so how much of them is the code is not
known.

## Budgets

`budgets.json` is not derived from this run: it still holds the 79 measurements of the 2026-10-10
baseline, 68 of them budgets and 11 tracked (ADR 0021, decision 19). This run's six exceeded preview
figures lie 26 to 59 % above 2026-10-10's medians, 28 to 60 % in the W13 code's runs, and the cause
is not established (above). Derived from this run with the rules of ADR 0021's decision 5
(`Test-BenchBudgets.ps1 -Create -BaselineDir docs\performance\data\2026-10-15`, which this folder's
quiet records allow without `-AllowBusyMachine`), their budgets would sit 57 to 99 % above those
medians:

A preview regression of that size would then pass if the machine returned to the state in which the
2026-10-10 preview scenario was measured, and a budget is not loosened on an unexplained change of
the machine's state. Every other budget of 2026-10-10 held but the Z 6's exposure step (above), the
warm start's included, now measured last and after a quiet wait, which the ADR 0021 amendment "a
quiet machine is required, and judged per process" had left open: 0.76 s to the window (at most
1,090 ms), 0.86 s to the first frame (1,200 ms), 188 MiB (193 MiB). The budgets are derived again
from the baseline that closes COR-5.

The over-images statistics (the analysis and the export per image) are still gated on the median of
their images' repetition CVs. ADR 0021's decision 9 planned to gate them on the repetition
variability of the statistic itself, which `Test-BenchBudgets.ps1` does not compute; computed by
hand on this run it is 0.2 to 2.2 % (median and p95: the analysis 0.2 and 0.4 %, the JPEG export
0.3 and 0.4 %, the 16-bit TIFF export 2.2 and 1.8 %), so the same six statistics would be budgets.

## What is not measured

- **The display, the session and the window.** `machine.json` records neither whether Lucent's
  window was on screen nor whether the display was off or the session locked, nor the timer
  resolution in effect, and the preview figures changed with the machine's state in a way the record
  does not explain (above). COR-5 stays open until a baseline is measured with the display on, the
  session unlocked and Lucent's windows visible, and recorded as such; until then an exceeded budget
  is checked with the A/B measurement (ADR 0021, decision 20) before it is taken for a regression.
- **The blueprint's 16 GB reference laptop.** Everything here comes from the 12 GB development
  laptop; the budgets apply to it only.
- **The other scenarios against the earlier code.** The A/B measurement covered the preview
  scenario; the other differences from 2026-10-10 above are not divided between the code and the
  machine.
- **A start after a reboot** (Windows' DLLs and the driver uncached); the cold start measures a
  first start after installation.
- **GPU paths:** Lucent renders on the CPU only.
- **Long interactive sessions** (hours of editing, memory over time), the editor while a batch runs,
  scrolling a library of thousands of photos, and the UI thread during batches beyond its largest
  gap per run.
- **Batches to network or removable destinations, 16-bit TIFF batches of all fixtures, Display P3,
  related-shot consistency (`--keep-consistent`) and Analyse only.**
- **Photos above 61 MP** in these scenarios, the Nikon Z 8 HE files (LibRaw cannot decode them) and,
  in batches, the Insta360 One X (left out as unsupported).
- **The 1,000-file batch resilience run** (not repeated, above), and with it disk-full and drive
  removal, which the batch tests cover (ADR 0012).
- **Installer and first-run costs** beyond the cold start.
